012 小时

先把事务讲明白，别急着串链 ★★

为什么做：如果把 valid 当成接收条件，忙时会重写数据；如果把 commit 提前，memory 会记录上一笔结果。功能语义不明确，DFT 改造前后就没有可靠的等价性基线。

最小背景：ready/valid 像生产者与消费者约定的提交协议：只有二者同时为 1 的采样边沿才成交。寄存器之间的组合逻辑像纯函数；多个寄存器的非阻塞赋值像一次原子状态提交。硬件不是从上到下逐行执行的函数调用。

从上到下读：在 找 accept = data_valid & data_ready；到 确认只在 accept 装载；再读 的状态，最后看 和 memory 的使能。

模块 / 输入负责做什么不能越过的边界
ingress / accept、data_in在握手边沿保存 32 位 word_q不解码 cfg，不因 valid 单独更新
FSM / acceptIDLE → EXEC → COMMIT → IDLE不保存业务数据，不硬编码向量
mix / word_q、key、execute四路模 2³² 累加，异或为 result_q不是 CRC 或加密；只在 execute 更新
cfg / 配置写请求保存 key、soft_reset、mem_raddr；组合读状态不是 APB/AXI；key 仅允许空闲时改
top / commit连接 memory 写使能并推进写指针不把 memory 宏内部当作 scan cell

重点与难点：在 95 ns 进入 COMMIT 时，组合 data_out_valid 变为 1；memory 的正沿过程已读取旧 commit=0，因此这拍不写。105 ns 正沿读取此前 commit=1，才写 result 和推进指针。不能只看“状态变成 COMMIT”的文字就认为同一边沿已经写入。

备选方案、错误写法与真实代价

错误：在 ingress 用 if(data_valid)；在 busy 时改变输入，会覆盖正在消费的事务。正确条件是已成交的 accept。另一方案：可增加 FIFO 提升吞吐，但要新添 full/empty、存储和背压验证，本周单事务协议不需要。

同拍更新误解：结果与 lane 都使用 n0…n3 的组合值，而不是刚写入的 lane。若在参考模型里用旧 lane 的异或，就会少算本笔数据。独立参考应遵循事务规格，不能直接读取 DUT 内部 lane 充当预期。

★经验点：本 DUT 的最短接收间隔为 3 个 sys 周期（协议推导值）；当前 TB 故意留有驱动间隔，不用它声称峰值吞吐。若需求是每拍接收，应先重做流水线/背压契约，再讨论 scan 代价。

怎么验收：路线“一笔事务”中，90 ns 的外部 data_in 已变为 0xFFFFFFFF，word_q 仍为 0；95 ns result=0x8D60E266；105 ns write_pointer=1。运行完整功能 TB 仍须得到 PASS FUNCTIONAL_V0。

021.5 小时

两个逻辑锥：一个要回溯，一个没有解 ★★★

为什么做：ATPG 需要同时激活故障并把差异传出去。重汇聚的两条路径共享输入，局部传播条件可能互相冲突；冗余锥则可能根本不存在检测向量。把两者混为“多跑些随机数”会浪费时间，也会误报算法缺陷。

最小背景：故障激活是让正常节点值与 stuck-at 固定值相反。传播是让差异穿过下游门。例如 OR 的其他输入要为 0，AND 的其他输入要为 1。重汇聚像同一个变量在两条约束中反复出现，局部满足不保证全局满足。

实际结构： 中 p=a&b; q=~a&c; reconv=p|q。对 q/SA1 取 a=1 激活 q=0，传播要求 p=0；若先选 a=0 就与已有 a=1 冲突，回退选 b=0。c 可任取；向量 abc=100 的正常/故障输出为 0/1。

冗余证明：r=d&e; redundant=d|r=d。r/SA0 的激活需要 d=e=1，此时 d 已将 OR 输出固定为 1，差异永远出不去。r/SA1 则能在 d=0 时检测。因此“冗余逻辑”不等于“所有相关故障都不可测”。

故障检测输入的推导32 个 abcde 组合中的实测数
r/SA0激活与传播条件矛盾0
r/SA1d=0，a/b/c/e 自由16
q/SA1a=1,b=0,c 自由；或 a=0,c=0,b 自由；d/e 自由16

这些是“检测一个故障的输入组合数”，不是全芯片故障覆盖率。对该有限组合锥，穷举 32 组合加上逻辑证明可以判定 r/SA0 不可测；不能把这一结论推广到未知时序网表。

为什么要使用独立 d/e，而不复用 a/b？

若 r 和 p 都写成 a&b，综合器可能共享同一个 AND；于是“冗余节点”还能沿 reconv 被观测，本来的不可测证明不再成立。我们保留独立 d/e，并在 JSON 中检查 r 的 AND 驱动、吸收 OR 和唯一消费路径。只保留一个叫 r 的名字不够。

反模式：使用 keep 属性后直接宣布故障对象还在。正确做法：检查最终实例和连接；属性是要求，不是检查结果。若用普通布尔优化可能消掉冗余，这对功能面积是好事，但教学靶点就要随之更新。

force/release 边界：结构 TB 在真实模块的 wire 上注入一个故障，读取输出后立即 release，并为下一次正常基准留出事件传播时间。把强制值忘在网表中会污染后续实验；这不是完整 ATPG 引擎。

怎么验收：PASS W2_FAULT_TRUTH vectors=32 r_sa0=0 r_sa1=16 q_sa1=16。再用页面既有的回溯实验核对 abc=100。图、RTL、TB 和数学关系必须说同一件事。

032 小时

先列时钟来源，再谈“混串铁律” ★★★

为什么做：scan_en=1 只改变数据 MUX，不能让关闭的时钟自动出现；分频器还可能让移位期间少走几拍。时钟偏斜、边沿和门控方式影响数据是否在一个测试脉冲里被多推进一次。

最小背景：门控是决定时钟脉冲是否能到达寄存器，不等同寄存器 D 端的使能。正沿 ICG 的典型功能模型在低相位锁住 enable 的下一拍选择，高相位保持选择；这里的 latch+AND 只是等价行为结构，没有真实库 ICG 的时序与 TE 定义。

实际结构时钟 / 边沿关系与预期改造
入口、FSM、mix、cfg、shadowsys_clk 上升沿主功能域；scan 时需要明确测试协议
aux_count / toggleaux_clk 上升沿独立源，与 sys 不保证相位关系
slow.ticksdivider[1] 上升沿由 sys 逻辑 /4，示例周期 40 ns
gated_counter.countclk & enable_latched 上升沿功能门控；v1 需要受控打开，不是另一个自由频率源
neg_capture.sampledsys_clk 下降沿同一时钟的另一边沿，不等于异步域

操作：在回放的“门控时钟反例”看 17 ns 的 enable 改变。sys 在 15 ns 已经为高，直接 AND 立即产生额外上升沿，18 ns bad_count=1；低相位锁存仍关闭，good_count=0。到 25 ns 正常上升沿，才得到 good=1、bad=2。27 ns 再关 enable，直接 AND 把高脉冲截断；28 ns gated_clk=1、direct_clk=0。

TE、边沿顺序与 Lock-up 的判断边界

反模式：直接 clk & (enable | test_mode) 就称为无毛刺 ICG；test_mode 若高相位切换，仍可制造窄脉冲。后续做法：在被识别的门控结构上接测试使能，并把模式切换限定在安全协议窗口；真正工艺 ICG 的 TE 极性与时序看库模型。

边沿示例：在同相且固定的扫描波形下，常见安排是下降沿段在前、上升沿段在后，同时明确 SI/SO 采样窗口。若上升沿段接下降沿段，状态可能在同一宏周期继续前进半拍，但不能脱离波形直接判成必错。最终依据是各段 active edge、Tclk、clock skew、setup/hold 和锁存器透明电平。

★经验点：这一周不预设链数或每链 50/500/1000 的“标准答案”。工业切链取决于扫描管脚、ATE 时长、时钟域隔离、物理距离和库单元。给定库、管脚预算与测试频率之前，没有可照搬的安全长度范围；后续用这些输入算方案。

怎么验收：PASS W2_ICG latched_count=1 direct_count=2 与 divider_period_ns=40；67 ns 负沿 sampled=0，71 ns sampled=A。STA 的 hold/setup 是否满足仍是未测项。

DFTCompiler/Tessent Scan 根据测试时钟、门控测试使能与时钟域约束进行检查和串链；TetraMAX II/Tessent ATPG 使用该时钟协议生成测试过程。Icarus 能复现本例事件边沿，却不保证真实窄脉冲能否触发、毛刺滤除或 skew 签核。跨域 Lock-up 要结合实际时钟波形与库时序，本周仅验证问题来源。

041 小时

跨域事件：同步到了，不等于永远不丢 ★★

为什么做：直接把一个 aux 域窄脉冲送入 sys，可能整段脉冲发生在两个目标采样边沿之间。双级同步能给亚稳态恢复留时间，但不能凭空看到从未采到的事件。

最小背景：toggle 把事件编码为状态翻转，翻转后的电平保留到下次事件。像分布式系统里的版本 bit：只要目标足够快，就能用新旧 bit 不同检测一次更新；两次翻转在目标采样前发生会抵消。

代码追踪： 依次是 aux_count、toggle、sync1、sync2、previous、event_pulse。sync2 ^ previous 产生一拍目标脉冲；第一同步级不能同时去驱动功能状态和第二同步级。

错误/正确/备选与经验依据

错误：把同步器数量=2 当作任意速率事件无损保证。当前可行：aux 每 16 拍翻转一次；示例 aux=14 ns，即事件间隔 224 ns，远大于 sys=10 ns 下的同步传播时间。另一方案：req/ack 握手能按协议避免覆盖，代价是返回路径和往返延迟；多位数据应采用明确的握手、异步 FIFO 等机制，不能给每个位各加两拍后就认为总线一致。

★经验点：同步级数与允许 MTBF、工艺、频率和数据翻转率有关。本例“两级”是行为教学选择，不是安全认证结论；软件式的固定重试次数类比不能替代模拟电路恢复时间。

怎么验收：结构 TB 在 1000 ns 统计 source_events=4 target_events=4，完整功能 TB 的 events_seen 也增长。数字事件数相等只证明本次激励；未进行模拟亚稳态或任意相位穷举。

CDC 审核与 DFTCompiler/Tessent 的测试协议规划相互衔接，职责不同。ATPG 必须知道同步寄存器是否扫描、如何捕获与屏蔽未知响应。当前脚本只数本例事件，不承担 CDC 静态签核；商业工具是否扫描某一级必须按项目策略和真实报告确认，不写成统一的 dont-touch 规则。

051 小时

内部复位：谁清零了状态，谁能把它放开 ★★

为什么做：如果扫描装载时 soft_reset 变为 1，core_rst_n 会立即变低，链中的状态被清掉；即使没有时钟边沿也会发生。单看正常上电仿真很容易漏掉这条路径。

最小背景：异步复位断言不等待时钟；撤销涉及 recovery/removal 要求。它像绕过事务提交的强制清空接口。功能上方便，不代表测试时可以随意触发或释放。

实际路径：cfg_wdata[0] → soft_reset → AND/NOT → core_rst_n → ingress/FSM/mix/count/slow/neg/shadow。cfg、分频器和 CDC 使用 rst_n_ext；这是为了复位控制寄存器在核心被清零时仍能写回 0。新手若把 cfg 也接 core_rst_n，可能让控制位自清，改变复位脉冲语义。

原始问题与后续修复，分别验证

v0 问题：core_rst_n = rst_n_ext & ~soft_reset 的内部来源不能保证测试时一直保持非活动。v1 方向：显式测试复位选择，让测试协议接管；还要说明 test_mode 何时切换及如何保证撤销安全。此处只是修复计划，不把一行三元表达式当作已实现、已签核的复位电路。

复现：72 ns 拉高 soft_reset，当时没有 sys/aux 活动边沿；73 ns 观察 neg_sample=0 和 slow_ticks=0。74 ns 释放后，80 ns 下降沿恢复采样，81 ns neg_sample=A。波形证明异步断言，不能证明真实 recovery/removal 裕量。

怎么验收：路线“负沿采样与内部复位”复现 67/71/73/81 ns 的 0/A/0/A；完整功能 TB 保留 PASS SOFT_RESET_RECOVERY，证明通过配置端口解除复位仍可接受新事务。

工业界工具对标卡 · 异步控制可测性 ↗

DFTCompiler/Tessent 的检查需要理解异步控制在 shift/capture 中是否可控，ATPG 协议也要指定复位如何保持。本例 TB 只证明内部复位会清零、能恢复，不能替代门级工业 DRC 或恢复/移除时序检查。后续自研 DRC 会把受支持的规则逐条编码并附反例。

061.5 小时

Memory 输出不再是 X，不代表外围都测到了 ★★★

为什么做：SRAM 宏没有普通 DFF 的可串接接口；未初始化内容会产生未知值。如果为消掉波形的 X 而强制初始化或屏蔽全部输出，既可能改变真实硬件边界，又可能遮住外围故障。

最小背景：黑盒只承诺端口和行为契约，内部实现由宏库提供。read-first 表示同址读写时先返回旧内容。Shadow Logic 是被宏挡在不易控制/观察位置的周边组合与状态逻辑，像被外部依赖隔住的代码路径。

读源码： 在仿真时有数组和读寄存器；定义 SYNTHESIS 后只保留带 blackbox 属性的端口壳。 在 sys 正沿计算 ^rdata，读取的是本沿之前的 rdata。

观察时刻memory rdatashadow parity因果
36 nsXX35 ns 写入地址 3 的数据 1，但同址 read-first 仍返回未初始化旧值
46 ns0x00000001X45 ns memory 更新读寄存器；shadow 同沿仍读取之前的 X
56 ns0x00000001155 ns shadow 才计算已知数据的奇偶校验
错误写法 vs 正确边界：三种容易混淆的“修复”

错误 1：给仿真数组全部写零，声称解决 X。后果：从测试中隐藏未初始化风险；综合黑盒并不会自动获得这个复位能力。当前正确边界：保留 X，用四态比较断言它确实出现。

错误 2：把 memory 输出统一 AND 成 0，声称提高 coverage。后果：观察路径也可能被遮住。v2 方向：bypass 提供可控数据，额外观察路径覆盖 Shadow Logic；重新计算新增测试结构的故障分母。

错误 3：只加 bypass、不管写使能。后果：移位状态可能伪造 commit，破坏 memory 内容。v2 方向：根据 shift/capture 协议门控写使能，并独立验证功能模式下仍正常写入。

★经验点：bypass 位置需要兼顾面积、功能时序与周边覆盖。只在宏输出附近加 MUX 可以隔离 X，但不能自动保证地址/写数据锥可观察。本例宏内部故障排除在 Scan/ATPG 主线之外；MBIST 仅在最后的工业全景介绍。

怎么验收：PASS W2_MEMORY read_first=1 shadow_extra_cycle=1，加上 JSON 中 memory_blackbox_instances=1。必须同时保留功能模型与综合黑盒这两类证据。
